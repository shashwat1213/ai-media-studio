## What got built
- `infra/bootstrap/`: versioned, encrypted, private S3 bucket for Terraform state (S3-native locking).
- `infra/terraform/`: VPC (2 AZs, no NAT), RDS Postgres 16, private S3 media bucket, 3 ECR repos
  (immutable tags, scan on push, keep 10), ECS cluster with `app` (nginx+api), `worker` (Spot),
  `redis` (Cloud Map DNS) services and a `migrate` one-off task, internal ALB, CloudFront with a VPC
  origin, SSM SecureString secrets (generated by Terraform), least-privilege IAM, GitHub OIDC deploy
  role, budget alert.
- `.github/workflows/deploy.yml`: CI green on main → build/push SHA-tagged images → migrate → rolling
  deploy → live smoke test.
- `scripts/aws/`: `rollout.sh`, `up.sh`, `down.sh`, `status.sh` (CI and humans use the same scripts).
- CI: `infra` job (terraform fmt/validate + checkov), Trivy scan of the api + web images.
- App: `TRUST_PROXY_HOPS`; runtime image without npm. Docs: `COST.md`, `infra/README.md`.

## Decisions & trade-offs (interview material)

**1. Terraform, with remote state.** The state maps resources to real ids and holds generated
secrets, so it lives in a private, encrypted, versioned bucket, not on a laptop. Since Terraform 1.10,
S3 can lock the state itself (`use_lockfile`), so the classic DynamoDB lock table isn't needed.
Bootstrap is its own tiny stack because the state bucket can't store its own creation state.

**2. CloudFront in front of an *internal* ALB (VPC origin).** HTTPS needs a certificate, and a
certificate needs a domain. CloudFront gives HTTPS on `*.cloudfront.net` for free, and with a VPC
origin the ALB sits in private subnets with **no public address**. The ALB security group only
admits CloudFront's managed prefix list. Bonus: `/assets/*` (content-hashed) is cached at the edge.

**3. No NAT Gateway.** Tasks need outbound internet (ECR pulls, SSM, OpenRouter). A NAT Gateway is
~$33/month per AZ before any traffic, more than the rest of the stack. Instead, tasks sit in public
subnets with a public IP, and their security group allows **no inbound except from the ALB**. A public
IP doesn't mean "reachable": the firewall decides. The trade-off is ~$3.65/month per task for IPv4.

**4. nginx + api in one task.** Same web image and nginx template as compose, with
`API_UPSTREAM=http://127.0.0.1:4000` (containers in an awsvpc task share localhost). The browser stays
same-origin, so cookies are first-party and there's no CORS. Cost: web and api scale together, which
is fine because nginx is negligible.

**5. Redis as a Fargate task, not ElastiCache.** The queue carries only job ids; Postgres is the source
of truth (04 learnings #3). If the Redis task restarts and loses queued ids, the stuck-job sweeper
fails + refunds those jobs within `JOB_TIMEOUT_MINUTES`. Credits are never lost; the worst case is a
user retrying. That's an acceptable risk for ~$12/month saved. Persistence is off on purpose (no
volume on Fargate without EFS). Redis is found via Cloud Map private DNS (`redis.ams.internal`).

**6. Worker on Fargate Spot.** Spot tasks can be reclaimed with a 2-minute SIGTERM. The worker
already handles that: graceful shutdown finishes in-flight jobs (stopTimeout 35 s), BullMQ re-delivers
anything unfinished, and guarded state transitions + deterministic S3 keys make a redo safe. The
earlier correctness work is what makes the cheap option safe.

**7. Migrations as a one-off task BEFORE the rollout, and they gate it.** New code may need new
columns, so migrations run first. If `prisma migrate deploy` exits non-zero, the script stops and no
service changes. During a rolling deploy, old and new code run side by side, so migrations must be
backwards compatible: **expand → deploy → contract** (add the nullable column; ship code that uses it;
drop the old column in a later release). The migration CLI lives in its own image, not in the one that
serves traffic.

**8. Rolling deploy + circuit breaker.** `app`: min 100% / max 200%. The new task starts, must pass the
ALB health check (`/api/health` through nginx = api + DB up), and only then does the old one drain
(20 s deregistration delay). The deployment circuit breaker rolls back a revision that never gets
healthy. Graceful shutdown (Phase 4, tini + SIGTERM) is what makes the drain lossless.

**9. GitHub OIDC instead of access keys.** Each workflow run gets a short-lived signed token from
GitHub; AWS checks the issuer, audience and **subject** (`repo:shashwat1213/ai-media-studio:environment:production`)
and returns 1-hour credentials. Nothing long-lived to leak or rotate. A fork, a PR or another repo
can't assume the role. Third-party actions in the deploy job are pinned to commit SHAs, because a
moved tag could otherwise run new code with AWS credentials.

**10. Least privilege, concretely.** Task role: Get/Put/Delete on `media-bucket/users/*` + ListBucket,
nothing else. Execution role: ECR pull, logs, and `ssm:GetParameters` under `/ams/prod/*` only.
Deploy role: push to 3 named repos; register task defs; update services in one cluster; `RunTask`
only for the `ams-migrate` family in that cluster; `iam:PassRole` only for the two task roles and only
to `ecs-tasks.amazonaws.com`.

**11. Secrets: SSM Parameter Store, generated by Terraform.** Standard SecureString parameters are
free (Secrets Manager is $0.40/secret/month); ECS injects both the same way (`secrets: valueFrom`), so
values never appear in the task definition, the image, git or GitHub. DB password, JWT secret and
metrics token are `random_password`s. The OpenRouter key is set by hand (`ignore_changes`), so it never
passes through Terraform. Honest caveat: generated secrets do live in the Terraform state, which is
why the state bucket is private and encrypted.

**12. Immutable image tags = git SHA.** A tag always means the same bytes, ECR refuses overwrites, and
a rollback is "deploy an older SHA". The live SHA is recorded in SSM (`IMAGE_TAG`), and Terraform reads
it when building task definitions, so a later `terraform apply` never silently rolls the app back to
an old image. Ownership split: Terraform owns the shape; the pipeline owns the tag and the desired
count (`ignore_changes`).

**13. Real client IP behind three proxies (a bug found before it shipped).** On AWS the chain is
CloudFront → ALB → nginx → api. Express had `trust proxy = 1`, so `req.ip` would have been the ALB's
address, and **every user would share one per-IP rate limit**: one person's failed logins would lock
everybody out. Now it's configurable (`TRUST_PROXY_HOPS=3` on AWS). Too high would let clients spoof
their IP via `X-Forwarded-For`. A test reproduces the shared-bucket bug at 1 hop and shows separate
buckets at 3.

**14. Security scanning in CI.** checkov scans the Terraform; every skip is written down with a
reason, so "we accept this risk" is a reviewed decision, not an oversight. Trivy gates on
HIGH/CRITICAL *with a fix available*: unfixed CVEs can't be acted on and would make the gate flaky.

**15. Cost as a design input.** See `COST.md`: ~$75/month running 24×7 (Sydney), ~$23 paused (the ALB keeps
billing), ~$0 destroyed. `teardown_friendly = true` makes `terraform destroy` complete (no final DB
snapshot, buckets/repos force-emptied). That's right for a portfolio project and wrong for real data,
so it's a single variable to flip.

## Deviations from 00_PROJECT_BASE
- **SSM Parameter Store** instead of Secrets Manager (the base allowed "Secrets Manager/SSM").
- **CloudFront + internal ALB** instead of a public ALB; the SPA is served by nginx in the app task, not S3.
- **Redis on Fargate** (the base allowed either; the trade-off is logged above as required).
- Region **ap-southeast-2** (Sydney). The plan was Mumbai, but the account uses the new AWS experience, where a project is locked to one selected Region. CloudFront is global, so users in India are still served from nearby edges; only uncached requests (API calls) travel to Sydney (~120-150 ms extra round trip from India).

## Known gaps / follow-ups
- Not applied to AWS yet. Needs the owner's account + review of `terraform plan` (billable).
- Single environment (prod). A staging environment would be a second `env` with its own state key.
- Rate limiter is still in-memory per task; with >1 app task, move it to Redis (`rate-limit-redis`).
- No custom domain (would add an ACM certificate + Route 53, and allow HTTPS to the ALB).
- RDS IAM authentication and KMS customer-managed keys skipped (cost/complexity; see `.checkov.yaml`).
- x86_64 only. Graviton (arm64) Fargate is ~20% cheaper and needs multi-arch builds (bcrypt +
  Prisma musl engines must be verified on arm64).
